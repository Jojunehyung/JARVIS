## Goal

The user's words, translated: "(1) let me also store document summaries, and before a meeting, after grasping the content, tell me what to check during the meeting; (2) every day, make me read through everything I need to know and check so far." Three things: (1) **documents** — a record `{ title, source?, summary }` attached to a meeting project or to none, listed in the `미팅` tab per project and in the `프로젝트 없음 · 긴급 메모` group, opened in a view/edit sheet, deleted after a confirm by title; (2) **pre-meeting checks** (`확인할 것`) on a schedule event — a checklist the user adds to by hand on the prep card and in the event sheet, or imports from a copy/paste AI reply through a third bridge packet (`AI에게 회의 준비 묻기`) that carries the project's minutes, documents, linked tasks and same-client contracts; when minutes are written for that event, `확인할 것 가져오기` copies the checks into the follow-up item editor; (3) a **daily reader** (`오늘 읽을 것`) — a full-content modal, not counts, that opens once a day in the briefing's place and from a button any time, derived at render and storing nothing per day. Everything is a record or a derivation: nothing here pays, promotes, completes a task, or reaches `computeGrades` / `krProgress` / `todoOf` / `calendarExportOf`.

## Decisions the user made today (final — record, do not reopen)

1. **Documents attach to projects, and may have none.** Top-level `documents: [{ id, projectId: string | null, title (≤ 60), source? (≤ 120 — a file name or link, text only; no file is stored), summary (≤ 5,000), addedAt("YYYY-MM-DD") }]`. Listed in the `미팅` tab inside each project section as `문서 {n}건` with a `문서 추가` button, and in the `프로젝트 없음 · 긴급 메모` group the same way. A document has a view/edit sheet; delete is confirmed by title.
2. **Checks live on the schedule entry.** `events[].checks: [{ id, text (≤ 200), done, source: "manual" | "ai" }]`, at most 30 per event. Shown and editable on the prep card (`MeetingPrepCard`) and in `EventDetailModal` for an event that maps to a project (by `projectId` or the title match); manual add in both. The prep card also lists the project's documents (title + the first ~100 chars of the summary; a tap opens the document sheet).
3. **AI prep is copy/paste only** (`AI에게 회의 준비 묻기` on the prep card): `buildPrepPacket` — the event line, the project's newest meetings (summary / decisions / open follow-ups / latest progress; a hidden meeting as date + title only, as `buildWorkPacket` does), the project's document summaries, open tasks linked to those meetings, contracts of the project's client when derivable, and the existing checks so they are not repeated; own cap 20,000; never the profile identifiers, never a transcript. Head rules: facts only, `해요체`, propose only check items (a question / open point / risk / thing to bring), JSON `{"checks":[{"text":"...","basis":"근거 한 줄"}],"note":"한 줄"}`. `parsePrepReply` reads only `checks`; a duplicate of an existing check (normalised text) is refused; `PrepBridgeModal` reuses the shared panes; ticked items register with `source: "ai"`. A **Rule 7 amendment** paragraph dated 2026-09-17 goes into `core-beliefs.md` in the same form as the work-proposal amendment; the heading count stays 19.
4. **Daily reader, no confirmation feature.** A full-content reader modal ("like a newspaper on the first run of the day, and openable any time with a button"); the user **explicitly declined** a per-item tick/confirm feature and anything stored per day. It replaces the briefing's once-a-day auto-open; a button sits on the profile tab's CV card and inside the briefing. When minutes are written for an event, `확인할 것 가져오기` copies the event's checks into the follow-up editor (`mine: false`, text as is); the event's checks stay.

## Defaults the planner set (stated so the user can change them; none is open for the implementer)

- **Shape: top-level `documents[]`, not `meetingProjects[].documents`.** A project-less document must exist (decision 1), so nesting would need a second home for it; `meetings[]` already solved the same problem with `projectId: null`, and every reader here filters by `projectId` the way `MeetingsTab` groups minutes. One array also means one `recordFits` guard per document, one `removeProject` guard (a project with documents is not deletable — below), and moving a document between projects is a field edit, not a move between arrays. `documents` is added by the v27 block as `[]`; `addedAt` is the record's date (the day it was added; there is no separate `createdAt`).
- **`checks` is optional with no backfill**, exactly like `events[].projectId` (v26): the v27 block adds only `documents`; `checks` is written the first time a check is added, and every reader uses `ev.checks || []`. The block stays one line, and a save that never used checks never grows by the key. The `@schema` block documents it as `checks?`.
- **Checks belong to the event record, not to an occurrence.** A weekly event carries the same checklist to every occurrence; a check ticked this week is still ticked next week until the user unticks or deletes it. Recorded as TD-61 (accepted — an occurrence-keyed checklist would need a date map on the event for a use the user has not asked for).
- **Reader title: `오늘 읽을 것`**, modal title `오늘 읽을 것 — {today}`, button copy `오늘 읽을 것 ›`. Not `오늘의 신문`: "newspaper" is a metaphor for a screen that states nothing but the saved state, and every other title in the app names its content literally (`오늘 브리핑`, `오늘 회의 준비`, `오늘 업무`). Not `오늘의 확인`: nothing is confirmed (decision 4). Facts only ([Rule 13](../../design-docs/core-beliefs.md#rule-13)).
- **The briefing is a link, not a section.** The reader's last row is a `브리핑 ›` button that opens `BriefingModal`; the briefing's nine sections, its footer (`AI에게 보내기`, `일지 쓰기`) and its journal/review routes stay where they are, unduplicated. Two of the reader's sections (`계약·입금 미확인`, `뒤처진 목표 페이스`) reuse `buildBriefing`'s own `biz` and `goals` items, so the two screens cannot state a different number.
- **One daily marker, `act.briefingSeen`, reused unchanged.** The root's boot and day-change effects open the **reader** when `act.briefingSeen !== today`; closing the reader (any way) or the briefing stamps it, through the existing `closeBriefing`, which already routes any `TAB_ACTIONS` type and opens any other `type` as a modal — so `{ type: "reader" }` and `{ type: "briefing" }` work through it with no change. No new field. The reader's `since` for `{since} 이후 새로 들어온 것` is `readerSince(act, today)`: `act.briefingSeen` when it is before today (the first run of the day sees everything since the last run); `shiftDay(today, -1)` when it equals today (the marker is stamped at close, so a second opening the same day falls back to yesterday — TD-62, accepted, stated by the section title); `shiftDay(today, -7)` when it is null (a fresh or demo save). The comparison is `>= since`, so an item dated on the last run's own day repeats rather than disappears ([Rule 13](../../design-docs/core-beliefs.md#rule-13)).
- **The prep-card block becomes a `div`.** Today the whole block is a `<button>` that opens the last meeting; a checklist with its own checkboxes, inputs and buttons cannot nest inside a button (invalid HTML, and React warns). The block becomes a `<div>` with an explicit `회의록 열기 ›` border button when there is a last meeting (TD-64; the `flow11.js` prep step that tapped the block is updated to tap the button).
- **A hidden meeting stays hidden in the prep packet** (`aiHidden` → date + title only), the transcript is never read (the shared meeting-line builder has no access to it), and the packet carries **no `## 이력` line at all** — meeting preparation needs no CV. An event's `place` and `note` are left out (the daily packet and the calendar file already leave them out) and a document's `source` is left out (a file name or a link can name a drive or a person; the title and the summary carry the content).
- **The `basis` of a proposal is folded into the check text** as `{text} — {basis}` when the result is ≤ 200 chars; otherwise the text is stored alone. The confirm row shows the basis on its second line either way, so nothing is hidden before the tick.
- **Client → contracts:** `dealsOfProject(state, project)` = deals whose trimmed `client` is non-empty and is a substring of `project.name` (the demo's `○○물산 재고 관리 자동화` contains `○○물산`). No stored link (TD-63, accepted — a `clientId` on projects is a schema field for a heuristic that works on the names the user already types).
- **Check deletion confirms** (`확인할 것을 삭제해요. 계속할까요?`), the progress-entry pattern; a document deletion confirms by title (`{title} 문서를 삭제해요. 계속할까요?`), the meeting pattern. `확인할 것 가져오기` skips a check whose trimmed text already equals a follow-up row's text and stops at the 30-row cap; the event's checks are not changed.
- **`removeProject` refuses a project with documents** the way it refuses one with minutes: the existing message (`회의록 {n}건이 있어 삭제할 수 없어요 — 회의록을 먼저 지워요.`, asserted by `flow10.js`) stays first; a project with documents but no minutes gets `문서 {n}건이 있어 삭제할 수 없어요 — 문서를 먼저 지워요.` `ProjectModal` gains a `documentCount` prop and disables `삭제` on either count.
- **Three new `modal.type`s** — `document`, `prepBridge`, `reader` — 30 → 33. Each is a distinct sheet with its own content; none can be folded into an existing one without a mode flag that the root would have to carry.
- **Storage guard:** every document write and every check write runs `recordFits` (nouns `문서를` / `확인할 것을`); `importChecks` measures every item it registers in one call, like `importWork`.
- **Demo:** two documents (one on `△△테크 문서 검색 AI`, one project-less), two checks on the demo's tomorrow event `○○물산 주간 점검` (one `manual`, one `ai` with a folded basis), and one **yesterday-dated, done** work item with a `result` so the reader's `오늘 업무` section states a `처리:` line without changing the demo `업무` counts line (`남음 2건 · 이월 0건 · 완료 1건 · AI 제안 1건` — yesterday's items are not in today's view; TD-57 still holds, there is still no carried row).

## Storage arithmetic (goes into the meetings-region comment, `documents.md`, `meetings.md`, `RELIABILITY.md`)

Unit: string length against `STORAGE_BUDGET` = 3,672,064 chars, as in the meetings region.

- `,"documents":[]` = **15 chars** once (v27).
- One document: `{"id":"xxxxxxxxxx","projectId":"xxxxxxxxxx","title":"","summary":"","addedAt":"YYYY-MM-DD"}` ≈ **91 chars** of overhead + title + summary (+ 1 comma between records); `,"source":""` adds 12 + the source; `"projectId":null` is 8 chars smaller. A full document (60 + 120 + 5,000) ≈ **5,283 chars** (+ 1 per line break in the summary, stored as `\n`). Typical (title 20, source 30, summary 600) ≈ **753 chars**. Two a week ≈ 100 a year ≈ 75 k chars (**2 %** of the budget a year); one full document per working day ≈ 250 × 5,283 ≈ 1.32 M (**36 %** a year).
- One check: `{"id":"xxxxxxxxxx","text":"","done":false,"source":"manual"}` ≈ **60 chars** + text; `,"checks":[]` adds 12 to an event the first time. A typical 40-char check ≈ 100; thirty full 200-char checks ≈ 30 × 260 + 29 ≈ **7,829 chars** on one event; ten such events ≈ 78 k (**2 %**).
- The reader stores nothing; `since` is read from the existing `act.briefingSeen`.
- `recordFits` measures a document record whole; `addCheck` / `importChecks` measure the event record as it will be written, against the length of the stored one (`prevLen`), so ticking or deleting a check never trips the guard.
