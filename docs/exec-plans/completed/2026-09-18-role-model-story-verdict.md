## Goal

The role model stops being a hand-built list of conditions the user must invent. The user writes **what they want as a story** (`원하는 모습`, free text, `해요체`), the app builds a **fifth bridge packet** from that story and its own facts (CV line, area grades, held certifications and exam bests, record counts, the existing stages, the last verdict), the user pastes the external chat's **critical, realistic verdict** back, and the app shows the verdict as an AI-stated, unverified opinion while letting the user **tick** which proposed stages, conditions and area requirement grades to save. The feeling of growth comes from facts, never mechanics: a **stage progress percentage** on the profile headline that moves with every record (mean over the current stage's conditions of `min(1, value/min)`), per-condition bars in the advice sheet, a **stage-completion overlay** shown exactly once per stage, a **verdict history with dates** and a delta line, and a **monthly re-assessment line** in `오늘 읽을 것`. The grade proximity (`roleGap`) stays exactly what it is — shown smaller beneath the headline, never merged with the stage figure ([Rule 14](../../design-docs/core-beliefs.md#rule-14)).

## Context — what the user asked (translated, recorded in substance)

"The role model should feel like I am really growing and getting closer — not by setting every condition by hand. I want to write what I want as a storyline in an AI prompt template (become the CEO of a company of such-and-such size; join company X), have the AI judge it critically and realistically (for a company: the actual hiring specs of the last three years; for founding: real success rates), and feel step-by-step progress. Today it is too vague and the progress % moves in steps that are too big."

## Decisions the user made today (final — record, do not reopen)

1. **No RPG mechanics** — no titles, levels, points, gold, randomness ([Rule 7](../../design-docs/core-beliefs.md#rule-7)). The feel of growth comes from facts: per-condition progress, a stage-completion overlay, verdict history with dates. The existing vocabulary `단계` / `조건` stays (not `챕터` / `퀘스트`).
2. **The AI proposes** stages, conditions and area requirement grades from the user's story; **the user ticks and saves**. The existing editor stays for fine edits (`세부 수정`).
3. **Re-assessment**: a monthly line in `오늘 읽을 것` plus on-demand from the advice sheet; verdict history kept with dates.
4. **Profile headline = stage progress %**, with the grade proximity (`roleGap`, formula untouched) shown smaller beneath. The two are never merged ([Rule 14](../../design-docs/core-beliefs.md#rule-14)).

## Defaults the planner set (stated so the user can change them; none is open for the implementer)

- **The headline percentage is the current stage's `pct`** (mean of `min(1, value/min)` over the current stage's conditions, floored so `100` prints only when the stage is met), not the journey figure. Reason: `pct` is the number that moves with each record the user adds, and it names the stage it measures; the journey figure `(k − 1 + pct/100) / n` moves at most `1/n` per stage and would blur which condition moved. The reset at a stage boundary is marked by the completion overlay, so it reads as a step taken, not a loss. The **journey figure is printed once**, in the advice sheet's stage block (`진행 {pct}% · 전체 {journey}%`), and nowhere else.
- **`stageK` on a verdict is the raw `roleStageOf().k`** (`n + 1` once every stage is met), computed on the state **after** the same save replaced the stages; display caps it at `n`. `stageN` is the stage count at that time.
- **`role.seenStageK` is a seen-stamp, not stored progress** ([Rule 9](../../design-docs/core-beliefs.md#rule-9)): it records which `k` the overlay was last shown for, exactly as `act.briefingSeen` records which day the reader was closed; `k` itself is always recomputed from the records, and `seenStageK` is read by nothing but the overlay effect. A save without it (every save that predates this change, or a stage set just written by the editor or the verdict sheet) is **stamped silently** — the overlay fires only when `k` rises between two renders of a stamped save. Every role write (`saveRole`, `importRoleVerdict`) stamps the new `k` in the same updater, so replacing the stages never fires an overlay; only a record write (a deal, a payment, a portfolio entry, a milestone, a lead, a notice, a certificate photo) that raises `k` does.
- **A third `Overlay` branch, `type: "stage"`**, is the design decision FRONTEND.md reserves for the user — decision 1 is that decision. No portrait, no trophy: a mono `STAGE` label in the place of `RANK UP`, the fact line `단계 완료 — {stage name}`, then `다음: {next stage name}` or `모든 단계 충족`, then `기록으로 계산된 완료입니다.` Cyan border like `gradeup`; auto-closes after the existing 2,400 ms.
- **The reader gains a tenth section `롤모델 판정`** (key `role`, after `뒤처진 목표 페이스`) rather than a briefing line: `buildBriefing` feeds the daily packet, and the AI's own probability must not travel back into a packet through the briefing. `buildBriefing` stays byte-identical. The section's action is `{ type: "roleAdvice" }` (`closeBriefing` opens any non-tab `modal.type` directly), or `{ type: "role" }` when no role model is set.
- **Ticking no stage keeps the existing stages** — a verdict can be saved alone. `role.targets` changes only for ticked area rows; an area row appears only when the proposed grade differs from the current target.
- **A stage with one invalid condition is rejected whole** (the sheet states why), so a half-stage is never saved silently; an area row with an unknown name or an out-of-range grade is rejected on its own.
- **`cert_held` arguments are normalised** to the official name `certByTitle(arg).n` (longest name first, [Rule 15](../../design-docs/core-beliefs.md#rule-15)) so `condValue`'s exact match against `heldCertsOf` works; no match → the stage is rejected with `자격 표에 없는 이름이에요`.
- **The raw reply is never stored** — not on the journal (`upsertReply` is not called), not on the verdict. The verdict record holds only the clipped `summary` / `basis` / `position` / `gaps` and the probability.
- **The packet's record counts are business-and-private only**: deals, milestones and every counted record pass the same `PACKET_TRACKS` filter as the other packets; a day-job record's existence is not counted. Portfolio entries, leads and notices carry no track (TD-78) and are counted whole — counts only, never a name.
- **Demo verdict dates are relative** (`shiftDay(today, -29)` ≈ 2026-08-20 on 2026-09-18, and `today`), not the literal `2026-08-20` the caller wrote, so the demo does not rot ([TD-75](../tech-debt-tracker.md) is the precedent for why absolute demo dates hurt).
- **The story textarea is the one free text sent verbatim.** Its caption and the send caption both say so; the packet's `## 이력` is `cvSummaryOf` only (degree · major, practice months · latest role title), as in every other packet — never the profile name, birth date, e-mail, phone, school or employer.
- **`modal.type` count 38 → 39** (`roleVerdict`). `RoleVerdictModal` is its own component (three steps: send · paste · confirm) sharing `PacketSendPane` / `ReplyPastePane` / `copyPacket`; `WorkBridgeModal` is not generalised further — its confirm view lists one kind of row, this one lists a verdict block plus two kinds of tickable rows.

## Storage arithmetic (goes into the region comment, `metrics-and-role-model.md`, `RELIABILITY.md`)

Unit: string length against `STORAGE_BUDGET` = 3,672,064 chars.

- **Story:** `,"story":""` = 11 chars + up to `ROLE_STORY_MAX` (2,000) → **≤ 2.0 k**, once.
