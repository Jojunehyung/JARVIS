# Korean public holidays in the month calendar

- Status: completed
- Date: 2026-09-11
- Needs approval: no — a new display-only table, no `CERTS`/`EXAMS`/matrix row, no `migrate` block, no `liferpg-*` key, no user data removed; the 2026–2027 scope is the user's own request.
- Agents: planner → implementer → cleanup → verifier → docs-syncer

## Goal
The month grid shipped today (commit `8a17bde`) is a plain date grid: `설날` and `추석` read like any other Tuesday. Add a display-only holiday layer to `ScheduleCalendar` — a holiday's and a Sunday's day number rose, a Saturday's sky, the holiday's name on the selected-day panel, and, in a month the table does not cover, one note saying which years it does. A holiday is never an event: nothing is registered, counted, briefed, paid or stored.

## Prompt
Add South Korean public holidays to the `달력` view of the `일정` tab in two phases; each phase ends at the gate below. Copy is Korean `해요체`, facts only ([Rule 13](../../design-docs/core-beliefs.md#rule-13)); identifiers, comments and docs are English (AGENTS §6). Tailwind v3 core utilities only — no arbitrary values, and the grid must still fit 390 px with no horizontal scroll (a cell is about 43 px).

**The table — Rule 6 in spirit, not in letter.** [Rule 6](../../design-docs/core-beliefs.md#rule-6) names the `CERTS`/`EXAMS` numeric tables and does not literally cover a new one; this plan does **not** amend the rule text (that would be its own decision). `HOLIDAYS` is therefore a new convention modelled on it: a frozen flat map `{ "YYYY-MM-DD": "설날" }` covering 2026 and 2027, using the officially published Korean names. The rows arrive verified, with citations, from the research agent and are copied verbatim — do not invent, interpolate or "correct" a date, and if the researched rows are not in hand when Phase A starts, stop and ask rather than ship placeholders. `설날` and `추석` follow the lunar calendar and `대체공휴일` are announced per year, so nothing here is computable. Do **not** register `HOLIDAYS` in `DATA_TABLES` (`tools/harness/lib/source.js`) — the generated symbol index would then label it "frozen by rules 6/15", which would be false — and do not touch `VOCAB_CONSTS` in `lang-check.js`: keep every comment English and never name a holiday in Korean in a comment. Above the table put an English header comment stating the coverage years, the source of record (`관보` announcements under `관공서의 공휴일에 관한 규정`), and that a year is added only from a cited government announcement, never by hand. Derive the coverage rather than repeating it — `const HOLIDAY_YEARS = [...new Set(Object.keys(HOLIDAYS).map((d) => d.slice(0, 4)))].sort();` — so adding 2028 rows updates the note by itself. Put both consts beside `CAL_RANGE_MONTHS` / `WEEKDAY_LABEL` at the top of the Schedule region and read them with a direct `HOLIDAYS[date]` lookup; add no helper function.

**Cell colours (Korean calendar convention).** In the grid cell, `dow` is the cell's column (`(firstDow + day - 1) % 7`, 0 = Sunday), and the day-number `span` keeps `text-xs font-mono` plus exactly one tone, in this precedence: today `text-amber-300 font-bold` (unchanged) → holiday `text-rose-400` → Sunday `text-rose-400` → Saturday `text-sky-400` → other `text-zinc-300`. Both tones already exist in the palette ([DESIGN.md](../../DESIGN.md)); this adds a second documented role to each, so no new hex and no new accent. **Today wins over the holiday tone**: today is a state mark that must stay one unambiguous colour (the E2E reads it as such), and the fact is not hidden — selecting today still names the holiday in the panel. The holiday tint and the rose `마감` marker cannot be confused and the spec must say why: the number is **text** (`text-rose-400`) on the cell's first line, the marker is a filled dot (`w-1.5 h-1.5 rounded-full bg-rose-400`) on the line below — different element, different line, text colour vs. fill.

**Selected-day panel.** When `HOLIDAYS[sel]` exists, render one extra line in `text-xs text-rose-400` **directly under** the existing mono line `{YYYY-MM-DD} · {n}건`, reading `공휴일 · {name}`. Do not append it to the mono line: that line is asserted verbatim by `flow7.js` (`panelLine()` matches `/^\d{4}-\d{2}-\d{2} · \d+건$/`), and the prefix `공휴일 · ` keeps a bare name from reading like an event title. Nothing else in the panel changes; a holiday with no event still shows `이 날짜에는 일정이 없어요.`

**Honesty outside the covered years.** Paging reaches ±`CAL_RANGE_MONTHS` (24) months, so uncovered months are reachable. There, **no holiday is marked at all** — weekend colouring still applies, because it is computed from the date, not from the table — and a single caption line renders **under the grid**, inside the same section (`text-xs text-zinc-500`, one text node, no nested spans so the E2E can match it whole): `공휴일은 {from}~{to}년만 표시해요.` It renders only when the shown month's year is outside `HOLIDAY_YEARS`, so a covered month gains no clutter. Under the grid rather than in the panel because it explains the grid.

**A holiday is not an event, and nothing is stored.** `HOLIDAYS` is read only by `ScheduleCalendar`. No `events[]` record, no `eventsOn` / `upcomingEvents` / `occurrencesOf` change, no counts-line change (`오늘 {n}건 · 이번 주 {n}건 · 지난 마감 {n}건` stays), no briefing line, no packet line, no task, goal, point, metric, trophy or streak effect, and nothing derived reaches `state` ([Rule 9](../../design-docs/core-beliefs.md#rule-9)). **The `목록` view shows nothing about holidays** — it answers "what is next" among the user's own records, every row there carries `완료 표시` / `수정` buttons and feeds the counts and the `이후` collapse, and a holiday is none of those; adding it would also oblige the briefing and the packet to carry it. **No schema change is expected and none is needed**: no new state field, no `migrate` block, no `v` bump, no `@schema` edit, no `flow4.js` fixture ([Rule 12](../../design-docs/core-beliefs.md#rule-12)). If implementation reveals a stored field is wanted (e.g. a "hide holidays" switch), stop — that is a new decision, not this plan. `demoState` is unchanged: the layer is static, so the demo shows it without demo data.

**Keeping the table honest.** The instruction lives in three places, all written in Phase B: the header comment above `HOLIDAYS`; a `Holidays` subsection in [schedule.md](../../product-specs/schedule.md) stating that the next year is appended once the government publishes that year's `공휴일` and `대체공휴일` dates (announced the preceding year), with the citation recorded in the decision-log row; and a dated row in [tech-debt-tracker.md](../tech-debt-tracker.md) — "extend `HOLIDAYS` through 2028 before 2027-12-31; until then months in 2028 show the coverage note and mark nothing". Until it is extended, the app states the limit instead of guessing.

```
panel holiday line   공휴일 · {name}                        e.g. 공휴일 · 설날
coverage note        공휴일은 {from}~{to}년만 표시해요.      e.g. 공휴일은 2026~2027년만 표시해요.
```
Unchanged and still exact: `선택한 날짜`, `{YYYY-MM-DD} · {n}건`, `이 날짜에는 일정이 없어요.`, `일정 추가`, `일 월 화 수 목 금 토`, the counts line, every `EventRow` and `EventModal` string. No new toast, no new modal copy, no new validation message.

**Acceptance criteria.** In a covered month every Sunday number is rose, every Saturday number is sky, other days stay zinc, today stays amber, and a holiday on a weekday is rose; selecting a holiday shows `공휴일 · {name}` under the counts line, which itself is unchanged; an uncovered month marks no holiday, keeps its weekend colours and shows the coverage note once; a covered month shows no note; `state`, `events`, the counts line, the briefing, the home card and the packet are byte-for-byte unaffected by the holiday layer; 390 px, no horizontal scroll.

**Verification per phase:** `npm run verify` (0 failed steps, 0 console errors), `npm run finish` exit 0, `npm run docs:gen && npm run docs:check`. No `--smoke` — no engine table, payout or matrix is touched. Finish protocol per AGENTS §5: cleanup → verifier → docs-syncer → report with a proposed commit message; commit only at an approved gate.

## Steps
1. **Phase A — data and rendering (`src/LifeManager.jsx` only).** `HOLIDAYS` + `HOLIDAY_YEARS` with the header comment beside `CAL_RANGE_MONTHS`; the day-number tone chain and `dow` in the grid cell; the `공휴일 · {name}` panel line; the coverage note under the grid. **Gate.**
2. **Phase B — E2E and docs.** Extend `tools/e2e/flow7.js` (never a `flow8.js`), reusing `clickExact`, `pickDay`, `panelLine`, `monthLabel`, `monthLabelIn`. First extend `gridCells` **without changing its contract** (existing steps assert one entry per day of the month): keep returning day buttons only, adding `dow` (grid position `index % 7`, computed over `grid.children` before filtering to buttons) and `tone` (`amber` | `rose` | `sky` | `zinc`, read from the number span's class). Then three steps: (a) *weekend colours in the current month* — every non-today cell with `dow === 0` is `rose`, every `dow === 6` is `sky`, at least one weekday cell is `zinc`, today is still `amber`; (b) *a holiday names itself* — page `›` at most 12 months for the first cell with `tone === "rose" && dow !== 0` (fail with "the holiday table must cover at least one holiday within 12 months of today" if none), select it, assert the panel carries a line starting `공휴일 · ` with a non-empty name and that `panelLine()` still matches its old pattern; (c) *outside the covered years* — click `›` until it is disabled (at most `CAL_RANGE_MONTHS` clicks; fail with "the holiday table must not reach beyond today + 24 months, or this step needs a new target month" if no note appears), assert the note matches `/^공휴일은 \d{4}~\d{4}년만 표시해요\.$/`, that no cell with `dow !== 0` is rose, that Sundays are still rose and Saturdays still sky, and that `오늘` returns to a covered month showing no note. Then every doc below. **Gate.**
