# The daily gate — `오늘의 관문`: read both screens to the end, pass a quiz on them, refresh today's work

Status: completed · 2026-09-24 · Route: planner → implementer → cleanup → verifier → docs-syncer · Needs approval: no beyond the four user decisions recorded below (no migrate block, no `liferpg-*` key, no data row, no deletion of a user record — `act.gate?` is an optional block of user-action stamps, pruned to the newest 60 days by the user's own decision). **The lockout risk is flagged explicitly** (decision 2, TD rows in Phase 3): a day without access to an external AI chat, or a parser bug, leaves the app unusable until the day passes or a deploy lands. The user chose this; the plan records it and does not soften it.

Three phases. **Phase 1** — state, the gate layer, read tracking on the two screens, the work-refresh wiring, and the E2E scaffolding that keeps the 269 existing steps unblocked. **Phase 2** — the sixth bridge packet (the quiz), its parser, `QuizModal`, the Rule 7 amendment, the rest of `flow12.js`, smoke. **Phase 3** — docs.

## Goal
From the first run of every day (weekends included) the app shows one full-screen gate, `오늘의 관문 — {today}`, in place of every tab and every sheet, until the user has (1) read both `오늘 읽을 것` and `이슈 목록` to their very end, (2) passed a multiple-choice quiz on that content — questions proposed by the external AI chat through a copy/paste packet, graded **locally** by the app, pass at 80 % or more of the questions — and (3) refreshed today's work (at least one `work[]` item created today, by the AI work bridge or by hand). `통과` then closes the gate and restores the app; closing and reopening the app the same day lands in the app, the next day in the gate again. There is no close, no skip and no settings access while the gate is open. Everything the gate stores is a stamp of a user action (a time, a score); everything else it shows is derived at render.

## User decisions (final, 2026-09-24)
1. **Pass threshold: 80 % or more** of the quiz questions — `need = Math.ceil(0.8 × total)` (7 questions → 6 correct; 5 → 4; 6 → 5; 8 → 7; 10 → 8). A failed attempt clears both read stamps: both screens must be re-read before a retry.
2. **No escape hatch.** No close, no skip, no settings access; the tab bar is not rendered while the gate is open. Consequences the user accepted, recorded in the tech-debt tracker (Phase 3): a day without AI access cannot be passed; a parser bug (or a model that never returns five valid questions) locks the user out until a deploy; backup export/import sits behind the gate too.
3. **Every day**, weekends included: the gate opens on the first run of the day and stays until passed; closing the app and reopening lands in the gate again.
4. **Reading = both** `오늘 읽을 것` and `이슈 목록` scrolled to the end (a sentinel at the very end of each screen must enter the viewport).

## Planner decisions (recorded here so the implementer does not re-decide)
1. **The gate is a layer, not a `modal.type`.** The app has one modal slot, and the gate's own five flows (reader, issue list, quiz, work bridge, work add) must render *in* that slot, above the gate. So `GateModal` renders whenever `gateActive` is true — beneath the slot, in place of `<main>` and `<nav>` — and there is no `{ type: "gate" }`. The user's default named `modal.type: "gate"`; this is the one deviation, and the reason is the single slot. `modal.type` count goes 40 → **41** (`quiz` only).
2. **`gateActive` is derived, once, in the root:** `phase === "main" && !!state && gateActiveOf(state, today)`, where `gateActiveOf = (state, today) => !!state?.profile && !gateEntryOf(state, today).passedAt`. Onboarding has no state → no gate. A restored backup or a planted save without today's stamp opens the gate at once. A day change while open re-evaluates by itself (`today` is state).
3. **Every `setModal` from outside the gate is dropped by one derived line, not by touching ~80 call sites:** rename the state pair to `const [modalRaw, setModal] = useState(null)` and derive `const modal = gateActive && modalRaw && !GATE_MODAL_TYPES.includes(modalRaw.type) ? null : modalRaw;` right after `gateActive`. Every existing `modal?.type === …` check keeps its name and now reads the filtered value; `GATE_MODAL_TYPES = ["reader", "issues", "quiz", "workBridge", "work"]`. `passGate` sets the raw slot to `null` so nothing stale surfaces when the gate lifts. `<main>` and `<nav>` are not rendered while `gateActive`, so no tab handler can fire; the filter is the defence in depth (mutation check 4).
4. **Stamps are `"HH:MM"` local times** (`hhmm()` — a new two-line utility beside `dstr`), keyed by date under `act.gate[date]`: `readReaderAt`, `readIssuesAt`, `quiz.at`, `passedAt`. Times make the step line `완료 08:12` a fact without a second field; the date is the key. The E2E scaffold plants `passedAt: "00:00"` — a synthetic stamp, stated in the README.
5. **The boot and day-change effects open the reader only when the gate is not active.** With the gate active the gate is the first screen; `?open=issues|reader` and the worker message still call `setModal({ type })` unchanged, and because both types are in `GATE_MODAL_TYPES` they open **in `gateRead` mode above the gate** — that is how the boot param "routes into the read step" with no new routing code.
6. **`gateRead` mode replaces every route on the two screens, it does not disable them one by one:** the reader renders no section `›`, no `이슈 목록 ›`, no `브리핑 ›`, no `닫기`; the issue list's rows are inert, `{n}건 더 ›` is plain text; each screen's footer is the one button `다 읽었어요`. The header X and the backdrop return to the gate **without a stamp** (`setModal(null)`, never `closeBriefing`). `다 읽었어요` on the reader stamps `readReaderAt` **and** `act.briefingSeen` (the one daily marker every other reader of "seen today" — `checkSummaryOf`, `readerSince`, the auto-open guard — already agrees on); on the issue list it stamps `readIssuesAt` only. Outside the gate both screens are byte-identical to today.
7. **The parsed quiz is held in root component state (`quizHeld`)**, never in `state`, because the quiz sheet, the reader and the issue list share the one modal slot — a re-read after a fail unmounts `QuizModal`, so `같은 문제 다시 풀기` needs the items to survive that unmount. It is cleared on `passGate`, on a day change and by a new paste; a reload loses it (decision 1's tech-debt row).
8. **Questions are shown all at once** (radio groups, `제출` enabled only when every question is answered) — one screen, one submit, one grading; no per-question feedback before submit.
9. **The gate history line lives in `SettingsModal`**, a new section `오늘의 관문` between `확인 알림` and `데이터 — 백업 · 초기화`. Not the reader: the reader is a derived reading of records and, inside the gate, must stay exactly the content the quiz is built from.
10. **`quiz.attempts` counts submits of the day**, across pastes and retries; a refused reply or an abandoned sheet is not an attempt.
11. **Pruning:** every gate stamp write drops `act.gate` keys older than `GATE_KEEP_DAYS` (60) before today — the app's own stamps, by the user's decision; never a record.
12. **Since-mode content in the quiz packet follows `act.workRefreshedAt` exactly as the work bridge does:** with a stamp, `workSinceOf(state, since).recent` (through `meetingPacketLines`), the older meetings' post-stamp progress, and the post-stamp documents; without one, the newest `QUIZ_PACKET_MEETINGS` (5) meeting-kind meetings and the newest `QUIZ_PACKET_DOCS` (5) documents. Training records enter as a section of their own (`workSinceOf` excludes them by design; the issue list shows them, so the quiz may ask about them).
