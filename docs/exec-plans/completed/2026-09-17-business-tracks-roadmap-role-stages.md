## Goal

Two bundles in one plan, committable phase by phase. **Bundle 1** — every project, document, event, work item and contract carries a **track** (`직장` the day job · `사업` the business · `개인` private life); the reader, the briefing and the work tab split their lists by track; **the day-job track never enters any AI packet**; the `사업` tab gains a **roadmap** of milestones with D-day, linked-work completion and pace; a **weekly time budget** for the business with a time log fed by work completions and a quick entry; contracts gain **lump-sum payment lines** (`계약금` first) beside the monthly `paidMonths`. **Bundle 2** — the role model is split into **nine detailed stages** with fact conditions the app evaluates from its own records, shown as `조건 충족 N/M` beside the untouched proximity percentage, with a new preset `의료 AI 솔루션 대표` that seeds them; a **sales pipeline** of hospital leads; **national-project notices**; the phone-calendar file gains follow-up dues, pre-meeting check reminders, milestone D-7, payment dues and notice deadlines; the weekly review states per-track counts and offers a copy/paste `주간 회고` packet whose reply proposes next week's business work items through the existing work-proposal path. Everything is a record or a derivation: nothing here pays, promotes, completes a task, moves a grade or the proximity number, or reaches `computeGrades` / `krProgress` / `goalProgress` / `roleGap` / `todoOf`.

## Defaults the planner set (stated so the user can change them; none is open for the implementer)

- **Track is a stored field on the record kinds the user named** — `meetingProjects`, `documents`, `events`, `work`, `deals` — and a **derived** value for a meeting with a project (`meetingTrack`: the project's track). A project-less memo (`projectId: null`) has no project to inherit from, so it carries its own optional `track`, chosen by a chip row that appears only while `없음 (긴급 메모)` is picked. Follow-up work items are stamped with the meeting's track at creation (`followUpWorkItem` gains a `track` argument) and keep their own field afterwards.
- **Backfill mapping (v28):** `track: "work"` on every existing project, document, event, work item and project-less memo; `track: "biz"` on every deal. The user then flips the SNUH project (and its documents, events and work items — each record separately; the app never cascades a track change) to `사업`. **New-record defaults:** `work` for a project, document, event, work item and memo; `biz` for a deal; a document or event whose form has a project picked follows that project's track until the user taps a track chip. The safe default is exclusion: a record wrongly left on `직장` is only absent from a packet, never leaked.
- **No project-level `aiAllowed` override.** A `work`-track record never enters any packet in this plan; the one per-record knob stays the existing `aiHidden` on a meeting (which now only matters inside `biz` / `personal`). A day-job project's prep card states `직장 트랙 — AI 패킷에 실리지 않아요` in place of the `AI에게 회의 준비 묻기` button. An override would be one tap between confidential hospital data and an external chat; recorded as TD-73, a backlog item the user may open later.
- **Order in the reader, the briefing and the work tab: `직장` first, then `사업`, then `개인`.** The reader opens before the working day; the day job's items are the ones that must not slip — the user's own condition for the whole plan — so they lead; the business follows as the second block; private items close. The same order everywhere, so a screen never reorders the user's day.
- **Splits are heads inside the existing sections, not new sections.** In the reader's `prep` / `work` / `followups` / `decisions` / `since` sections, items are stable-sorted by track and each non-empty track gets a head item (text `직장 {n}건` and so on, `head: true`); the work tab groups the day's rows the same way; the briefing prefixes event lines with the track and adds per-track counts to its count lines. Single-track sections (`계약·입금 미확인`, the new `사업 로드맵` and `사업 파이프라인 · 공고`) carry no heads.
- **Roadmap milestone status is set by the user** (`planned` / `active` / `done`, `doneAt` stamped on `done`); D-day, linked-work completion (`done/total` over live `workIds`) and pace are derived. **Stage order is stated, never enforced**: when an `active` milestone's stage is above the lowest stage that still has a not-done milestone, the roadmap view and the reader state `단계 순서: {a}단계 미완 · {b}단계 진행 중`; nothing blocks (sales can start while delivery runs).
- **Milestone pace mirrors `paceOf`'s thresholds** (±5 %p) with progress = linked work done ratio and elapsed = `createdAt → due` against `today` (pure — `elapsedRatio` reads `Date.now()`, so a `today`-based sibling is written, not a flag). No due → `기한 없음 — 페이스 계산 불가`; no linked work → `연결 업무 없음 — 페이스 계산 불가`.
- **`ROADMAP_SEED` uses absolute dates** from the situation table; the three the table leaves open are interpolated and marked in the seed's own condition text: stage 5 `2027-07-31`, stage 7 `2027-12-31`, stage 8 `2027-10-31` (the proposal precedes the award). Titles name no client. The demo seeds the same nine (so a demo run after 2027-12 shows every milestone overdue — TD-75, accepted).
- **Time log is the single source of the weekly sum.** `work[].minutes` is the item's own fact (shown on its sheet); the `timeLog[]` entry a completion appends (with `workId`) is what `weekMinutes` sums. `syncTimeLog` keeps exactly one entry per done item with minutes and none otherwise; the quick entry appends an entry with no `workId`. Nothing is double-counted because the sum never reads `work[].minutes`.
- **Payments are lump sums only** — `kind` is one of `deposit | interim | final | other` (`계약금` · `중도금` · `잔금` · `기타`); there is **no monthly kind** (the caller's draft listed `월`): a monthly instalment is already a `paidMonths` stamp, and a second record of the same month would double-count. `bizSummary`'s `thisMonth` / `collected` / `backlog` keep reading the billing rule only; payments get their own figures (`payDue`, `payOverdue`, `payPaidMonth`), printed on a third header line.
- **The quit condition is the last stage's conditions.** `전환 조건 충족 (1/1)` when stage 9 is met, else `전환 조건 미충족 (0/1)`.
- **Stage 7's revenue threshold** is a draft of 5,000,000 won a month (`monthly_revenue`), editable in the stage editor; the caller left it open.
- **Lead → deal conversion opens `DealModal` prefilled** (`client` = the lead's name, `status` = quote or won by the lead's stage, `track: "biz"`) rather than writing a deal silently — a `won` deal needs a period the lead does not carry, and `DealModal` already validates it. On registration the lead's `dealId` is set.
- **The calendar file gains five kinds and stays without money**: open follow-ups with a due date, an open-checks reminder the day before an occurrence, a milestone's due day and its D-7, unpaid payment dues **without the amount**, and open notice deadlines. Every track is included — the phone calendar is the user's own device and already carries day-job event titles. Leads stay out (a prospect's name is a person-adjacent identifier and `nextDue` is an internal reminder), as do rates, portfolio, documents, transcripts and the profile.
- **The `주간 회고` packet needs no Rule 7 amendment**: its reply is read by the unchanged `parseWorkReply` (key `work` only) and registered by `importWork`, which gains an optional `date` argument (next Monday) and a track argument (`biz`). The `AI에게 회고 묻기 ›` button is enabled only once this week's review is saved, so the packet reads the stored review, never a draft.
- **`WorkBridgeModal` is generalised** (`build`, `title`, `caption`, `importDate`, `importTrack` props) and rendered for both `workBridge` and `reviewBridge` — no second copy of the confirm view (`npm run finish` flags a ≥ 6-line duplicate).
- **Five new `modal.type`s** — `milestone`, `timeLog`, `lead`, `notice`, `reviewBridge` — 33 → 38. `ui.bizView` widens to `deals | rates | folio | roadmap | leads | notices`; `BizTab` still treats any other value as `deals`.

## Storage arithmetic (goes into the region comments, `business.md`, `daily-work.md`, `meetings.md`, `RELIABILITY.md`)

Unit: string length against `STORAGE_BUDGET` = 3,672,064 chars, as in the meetings region.

- **Track backfill (v28):** `,"track":"work"` = **15 chars** per project, document, event, work item and memo; `,"track":"biz"` = **14** per deal; `,"track":"personal"` = 19 when chosen. A save with 200 events, 500 work items, 20 projects, 50 documents, 20 deals and 10 memos grows by ≈ **12 k chars** (0.3 %).
- **Milestone:** `{"id":"…","title":"","status":"planned","dealIds":[],"documentIds":[],"workIds":[],"createdAt":"YYYY-MM-DD"}` ≈ **120 chars** of overhead + title; `,"due":"YYYY-MM-DD"` 19, `,"stage":9` 10, `,"condition":""` 15 + text, `,"doneAt":"…"` 21, `,"projectId":"…"` 25, each linked id 13. A full milestone (60 + 200 + three lists of 10) ≈ **900 chars**; typical (30-char title, a due, a stage, a 60-char condition, three links) ≈ **320**; the nine seeds ≈ **2.2 k** once.
- **Time-log entry:** `{"id":"…","date":"…","track":"biz","minutes":120,"createdAt":"…"}` ≈ **85 chars** (+ 22 with `workId`); one entry a working day ≈ 250 × 107 ≈ **27 k a year** (0.7 %); `,"minutes":120` on a work item adds **14**.
- **Payment line:** `{"id":"…","kind":"deposit","due":"YYYY-MM-DD","amount":30000000}` ≈ **75 chars** (+ 21 with `paidAt`); `,"payments":[]` adds 14 to a deal the first time; twelve full lines ≈ **1.2 k** on one deal.
- **Lead:** overhead ≈ **110** + name (≤ 60) + contact (13 + 80) + next action (16 + 120) + next due (22) + note (10 + 400) + deal id (22) + stage date (23) ≈ **880 full**, ≈ **260 typical**; fifty leads ≈ 13 k.
- **Notice:** overhead ≈ **110** + title 80 + agency 60 + posted date 24 + note 410 + ten document ids 130 ≈ **820 full**, ≈ **250 typical**; twenty a year ≈ 5 k.
- **Role stages:** nine stages × (`{"id":"…","name":"","conds":[]}` 30 + a 40-char name + two conditions × ≈ 45) ≈ **1.5 k** once, inside `role`.
- `,"settings":{"bizHoursPerWeek":20}` = **33 chars** once; the four empty arrays `,"milestones":[],"timeLog":[],"leads":[],"notices":[]` = **56** once.
