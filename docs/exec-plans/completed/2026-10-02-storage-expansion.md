## Goal
The app keeps everything in `localStorage` (about 5 M characters per origin), where photos (evidence, study artifacts, portfolio thumbnails, the profile photo) share the space with the records, and the records are capped by a 3.5 MB heuristic (`STORAGE_BUDGET`). The user approved three changes: (1) photos move to IndexedDB so `localStorage` is left to the records; (2) the record budget rises to 4.5 MB; (3) because a lost phone loses everything, the app states when the last backup was written and, once it is 7 days old or absent, says so in the reader and in the `확인 필요` notification. The change lives inside the storage adapter: every `store.get/set/del` call site stays byte-identical, the `liferpg-img-*` key convention stays ([rule 16](../../design-docs/core-beliefs.md#rule-16)), and when IndexedDB is unavailable the app behaves exactly as today.

## Planner decisions (recorded here so the implementer does not re-decide)
1. **Routing lives only in the adapter region.** A pure `routesToIdb(k)` = `typeof k === "string" && k.startsWith(IMG_PREFIX)` with `IMG_PREFIX = "liferpg-img-"`. `store.get/set/del` branch on it; every other key (the state `KEY`, anything else) takes today's code path verbatim. IndexedDB database `life-manager`, version 1, one object store `kv` (out-of-line keys), values stored as the plain string (the data URL) under the same key strings as today.
2. **One cached opener, failing to `localStorage`.** `imgDb()` returns a memoised promise of the `IDBDatabase` or `null`. `null` when `typeof indexedDB === "undefined"`, when `location.protocol === "file:"` (the single-file demo stays on `localStorage` deliberately), on `onerror`/`onblocked`, on an exception, or when `open` has not succeeded within `IDB_OPEN_MS = 1500` ms (private modes). With `null`, `store` behaves byte-for-byte as today for image keys too. The mode is decided once per page load.
3. **Read order for image keys: `mem` → IndexedDB → `localStorage`.** `mem[k]` is written synchronously at the start of every `set` and deleted by `del`, so it is the newest in-session value and covers the call sites that do not await `store.set` (7707, 7874, 11945, 13126). Then IndexedDB (authoritative), then a `localStorage` copy left by an older build (parsed exactly like today: an unparsable value reads as missing). Never throws.
4. **Write for image keys:** `mem[k] = v`; when `imgDb()` is non-null, `put` in a `readwrite` transaction and await `oncomplete`; on success remove the `localStorage` entry of **the same key** if one exists (it is the image the user just replaced — the user's own write, not the migration deletion, so not gated); on failure fall back to today's `localStorage.setItem` inside `try`. With `null`, today's path. `del` removes `mem`, the IndexedDB entry (when open) and the `localStorage` entry — so task removal, `clearImg`, portfolio delete and reset clear both backends with unchanged call sites (rule 16).
5. **The boot copy is injectable and ordered.** `copyLocalImages(local, idb, removeAfterVerify)` — `local = { keys(), get(k), remove(k) }`, `idb = { putIfAbsent(k, v), get(k) }` — for each `localStorage` key with `IMG_PREFIX`: parse the value (unparsable → `skipped`, never removed); `putIfAbsent` (one `readwrite` transaction: `get`, then `put` only when absent — a newer IndexedDB value written in the same session is never overwritten); then **read back** with `idb.get`; the copy is verified when the read-back is a non-empty string (equal to the parsed value, or the already-present IndexedDB value); only when verified **and** `removeAfterVerify` is true, `local.remove(k)`. Returns `{ copied, verified, kept, removed, skipped }`. The root calls it fire-and-forget after `readyRef.current = true` in the boot effect, through a thin wrapper `copyImagesToIdb()` that builds the two adapters (no-op when `imgDb()` is `null`). Idempotent; the StrictMode double run is harmless.
6. **Budget.** `STORAGE_BUDGET = 4.5 * 1024 * 1024` (4,718,592 chars). Its comment becomes "heuristic ceiling for the records (and, without IndexedDB, the photos) kept in `localStorage`; Chrome's per-origin quota is about 5.2 M chars". `storageUsedBytes`, `storageUsedWith` and `recordFits` are **unchanged**: they count what is actually in `localStorage`, so photos stop counting exactly when they leave it (IndexedDB mode, after removal) and keep counting while a `localStorage` copy remains or without IndexedDB. Excluding `liferpg-img-*` keys from the count is rejected: while copies remain, records could then pass the real quota.
7. **`saveImageChecked` per backend.** IndexedDB mode: no `STORAGE_BUDGET` check (photos no longer share the record budget; `THUMB_MAX_CHARS` still bounds each image); `await store.set(k, v)`; read back with the new `imageDurable(k)` (IndexedDB `get` non-null, else `persisted(k)` — never `mem`); failure → `await store.del(k)` and `{ ok: false, reason: "quota", usedMB }`. Fallback mode: today's body verbatim (budget + `persisted` read-back). The caller's two messages (12370–12372) are unchanged.
8. **Photo usage is summed lengths, not `navigator.storage.estimate()`.** `estimate()` is origin-wide (it includes the service-worker caches) and coarse; `imageStoreStats()` walks `kv` with a cursor and returns `{ mode: "idb" | "local", chars, count, localCopies }` — `chars` = Σ key length + value length (the unit `storageUsedBytes` uses, so `mbText` applies), `localCopies` = the number of `localStorage` keys with `IMG_PREFIX`. In fallback mode the photos are part of the record figure.
9. **E2E isolation.** `run.js` gains page-side `idbGet(k)`, `idbKeys()`, `idbPut(k, v)`, `idbClear()` (database `life-manager`, store `kv`) and `readImage(k)` = IndexedDB, else `JSON.parse(localStorage[k])`. Every flow that wipes the origin with `localStorage.clear()` before asserting images also calls `h.idbClear()`. `flow.js`'s reset step plants raw (non-JSON) values; they stay unreadable exactly as today and `store.del` still removes them — the implementer confirms by reading it and adds an `h.idbKeys()` assertion that `liferpg-img-profile` is gone.
10. **Copy, all facts** (rule 13), Korean UI copy verbatim, `해요체`:
    - Settings data section, below the existing caption, one `font-mono text-xs text-zinc-300` line: IndexedDB mode `저장 공간 {mbText(used)}MB / {mbText(STORAGE_BUDGET)}MB · 사진 {mbText(chars)}MB`; fallback mode `저장 공간 {mbText(used)}MB / {mbText(STORAGE_BUDGET)}MB · 사진 포함`; `used = storageUsedWith(state)`.
    - IndexedDB mode only, a `text-xs text-zinc-500` caption: `사진 저장소: 기기 사정으로 지워질 수 있어요 — 백업 파일에 포함돼요`.
    - While `localCopies > 0` in IndexedDB mode: `기록 공간에 남은 이전 사진 사본 {n}장`, plus ` · 백업을 내보내면 정리돼요` under option B only.
    - The backup line (Phase 2, `font-mono text-xs text-zinc-300`, directly above the two backup buttons): `backupLineOf(state, today)`.
    - `MeetingsTab` and `WorkTab`: the fragment becomes `저장 공간 {mbText(used)}MB / {mbText(STORAGE_BUDGET)}MB` (renders `4.5MB`). Portfolio footer: `포트폴리오 {n}건 · 대표 이미지 {m}장 · 저장 공간 {mbText(used)}MB / {mbText(STORAGE_BUDGET)}MB` (replacing `사용 중 (약 5MB 한도)`; `used` stays `storageUsedBytes()` read after the thumbnails load).
    - Unchanged on purpose (logged as tech debt): the persist-failure toast `저장에 실패했어요 — 저장 공간이 가득 찼어요. 백업을 내보낸 뒤 사진을 지워요.` and the `recordFits` refusal ending `백업을 내보낸 뒤 오래된 회의록이나 사진을 지워요.` — in IndexedDB mode deleting a photo frees record space only while its `localStorage` copy remains.
11. **The copy-removal options** (the approval question; the plan recommends **B**):
    - **A — remove on boot after read-back.** Space is freed at the first open after the update. From then on each migrated photo exists only in IndexedDB — evictable on Android under storage pressure — and in whatever backup file the user wrote earlier (possibly none, possibly old). Implementation: `COPY_REMOVE_ON_BOOT = true`.
    - **B — keep both copies until the next `백업 내보내기` (recommended).** After `downloadBlob` returns, the export removes the `localStorage` copy of every key it put into the file whose IndexedDB read-back is non-empty (`dropLocalImageCopies(keys)`, P2-B6). A migrated photo is never left only in evictable storage without a backup file written after the move. Cost: no record space is gained from existing photos until the user exports once (the settings copies line says so); the app cannot know the download completed (stated in the docs).
    - **C — never remove.** No deletion at all; existing photos keep using record space; only photos written after the update move. The settings copies line stays.
    New writes go to IndexedDB under every option; `COPY_REMOVE_ON_BOOT = false` under B and C.
12. **Backup reminder helpers** (pure, column 0, beside `checkSummaryOf`): `BACKUP_STALE_DAYS = 7`; `backupAgeOf(state, today)` → `null` when `state.act.backupAt` is absent or not `YYYY-MM-DD`, else `Math.max(0, daysBetween(backupAt, today))`; `backupStaleOf(state, today)` → `age === null || age >= BACKUP_STALE_DAYS`; `backupLineOf(state, today)` → `백업 기록 없음` | `마지막 백업 {date} · 오늘` (age 0) | `마지막 백업 {date} · {n}일 전`; `stampBackup(s, today)` → the same object when `s.act.backupAt === today`, else `{ ...s, act: { ...s.act, backupAt: today } }`.
13. **The stamp travels inside the file.** `exportBackup` builds `const next = stampBackup(state, today)`, writes `next` (not `state`) as the file's `state`, then `setState(next)`. An imported file therefore restores the date of the backup it is. A cancelled or failed download still stamps (the browser does not report it) — stated in the docs.
14. **The reader shows the backup section only when stale.** `buildReader` adds, before `prep` and only when `backupStaleOf`, `add("backup", "백업", [{ text: backupLineOf(state, today) }], { type: "settings" })`; a fresh backup leaves the reader byte-identical. (Alternative not taken: an always-present line — it would change every reader render and every gate read.) The `›` opens settings through the existing `closeBriefing` route (verify it routes a non-tab `type` to `setModal`).
15. **The notification adds one line when stale.** `checkSummaryOf` gains `backup: backupStaleOf ? backupLineOf : null` and `counts.backup` (0/1) added to `counts.total`; `checkNotificationOf` appends that text as the **last** body line and adds `backup` to the returned `counts`. Once stale, `counts.backup` stays 1, so this line alone does not re-buzz the phone daily.
16. **`demoState` seeds `act.backupAt: shiftDay(today, -2)`** so the demo's reader, notification and screenshots stay unchanged and settings states `· 2일 전`. `freshState` seeds nothing: a new user's reader states `백업 기록 없음` from day one — a fact.
