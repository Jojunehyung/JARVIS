# Reliability
<!-- src: E2E --><!-- src: SPEC-10 -->

Reliability for a local-only app means: the user's state survives every version, the build never ships a broken flow, and measurements are believed only when they are reproducible.

## Persistence and migrations
- State is one JSON object under `localStorage["liferpg-state-v1"]` (adapter `store`, memory fallback when storage is unavailable). Images are separate keys: `liferpg-img-profile`, `liferpg-img-ev-{taskId}`, `liferpg-img-study-{taskId}-{n}`, `liferpg-img-folio-{id}` — removed with the task/portfolio entry and on full reset.
- Every schema change adds a sequential `if (s.v < N)` block; existing blocks are frozen and a non-numeric `v` is normalised to 0 first ([Rule 12](design-docs/core-beliefs.md#rule-12)). The ledger is generated in [generated/db-schema.md](generated/db-schema.md).
- The E2E harness asserts migration from a v10 save, a save without `v`, a v13 save, a v14 save, a v15 save, a v16 save, a v17 save, a v18 save, a v19 save, a v20 save, a v21 save, a v22 save, a v23 save, a v24 save and a v25 save to the current version (v26), including field renames, trophy-kind conversion, the empty `events[]` a v15 save gains, the `ui.scheduleView: "list"` a v16 save gains with its events, journal and reviews intact, a v17 save's `kind: "meet"` task converting to a plain task with its title, difficulty, status and minutes `evidence` kept, a v18 save losing its life-metric store and check-in stamp while every other `act` stamp and record survives, a v19 save gaining empty `folio[]` / `rates[]` / `deals[]` and `ui.bizView: "deals"` while its `ui.scheduleView` and every other record survive, a v20 save (`v20 save → v21 CV records`) gaining empty `profile.edus[]` / `profile.careers[]` and empty `name`/`email`/`phone`/`null` `birth` while its legacy `age`, `edu`, `career`, `majorName` and every area, task, event, folio entry, journal entry, review and act stamp survive untouched, plus a second fixture proving a `profile: null` save (one that never finished onboarding) stays `profile === null` after migrating rather than being routed anywhere but `Onboarding`, a v21 save (`v21 save → v22 exam score fields`) gaining nothing but the retired `ui.scheduleView` key's removal — its `tasks[].score` and `exams.best[famId].score` stay absent, exactly as planted, rather than being invented — a v22 save (`v22 save → v23 meeting records`) gaining empty `meetingProjects[]` / `meetings[]` while every other key survives untouched, a v23 save (`v23 save → v24 meeting task links`) whose meeting gains `taskIds: []` with every other meeting field and key unchanged, a v24 save (`v24 save → v25 work items and meeting progress`) gaining empty `work: []` and, on a planted meeting that carries a task link, `progress: []` / `aiHidden: false`, with every other field and key unchanged, and a v25 save (`v25 save → v26 meeting follow-ups`) gaining `followUps: []` on a planted meeting that carries progress and `aiHidden: true`, with `actions`, `work` and `events` (none carrying a `projectId`) unchanged and no key added (`tools/e2e/flow4.js`). **The v22–v26 steps were added alongside their migration blocks (2026-09-16 for v22–v24, 2026-09-17 for v25 and v26) and have not been run since** — see "E2E policy" below.
- Storage keys are never renamed; they are the compatibility contract.
- Writing a portfolio image goes through its own guard, independent of the state save: a file-size cap before decoding, an aspect-preserving resize (`resizeImageFit`, never upscales) with one quality retry over an output-length cap, a budget check against a 3.5 MB heuristic ceiling, then a write that is read back to confirm it survived (`saveImageChecked`). Every failure still saves the record without its image and toasts why, and the state-save effect itself now runs the same read-back check (`persisted(KEY)`) and toasts `저장에 실패했어요` when a state write did not reach `localStorage`.
- Saving a meeting or a project (schema v23; a meeting's `taskIds` since v24, at most 132 chars for ten links, counted inside the same record) goes through the same 3.5 MB heuristic ceiling (`STORAGE_BUDGET`), counted in string length against `storageUsedWith(state)` — the current in-memory `state` serialised, not `storageUsedBytes()` alone, because the state save persists one render behind ([product-specs/meetings.md](product-specs/meetings.md)). A save that would cross the budget is refused before any write, the form stays open with everything typed, and the tab always states its own usage (`저장 공간 {mb}MB / 3.5MB`) so the ceiling is never a surprise.
- Since schema v25 (2026-09-17), the same guard — renamed `recordFits` — also covers a meeting's progress entries (`,"progress":[]` + `,"aiHidden":false` add 31 chars to every meeting; a full 300-char entry adds ≈ 345, thirty of them ≈ 10,380) and every work item (≈ 150–200 chars each, no per-day cap since 2026-09-17); the `업무` tab states its own `저장 공간` line the same way ([product-specs/daily-work.md](product-specs/daily-work.md)).
- Since schema v26 (2026-09-17), a meeting's follow-up items add `,"followUps":[]` (15 chars) plus ≈ 90–292 chars per item (a full 200-char item with a due date and a work link ≈ 292; thirty ≈ 8,760); `commitMeeting` checks the meeting record **plus every work item its reconcile creates** against the budget in one call before writing either, so a mine follow-up cannot register a work item the budget would refuse ([product-specs/meetings.md](product-specs/meetings.md)).

## Verification pipeline (`npm run verify`)
`tools/harness/verify.js`: `vite build` → `vite preview` on a free port → `tools/e2e/run.js` (puppeteer-core driving the installed Chrome/Edge; no browser download) → parse `tools/e2e/out/<tag>-result.json`. Exit 1 on any failed step or console error. `--smoke` runs the pure-function engine checks first (`tools/harness/smoke-logic.js`: table integrity, longest-name matching, stage-group differential payouts, documented scenario payouts, and the calendar-export file builder — byte-counted folding, TEXT escaping, the monthly-clamp expansion, `RRULE`/`EXDATE` construction, alarms, and privacy by construction; see [design-docs/calendar-export.md](design-docs/calendar-export.md)).

The calendar export's privacy and folding checks were mutation-tested the same way. Folding: counting characters (`.length`, UTF-16 code units) instead of UTF-8 octets failed the folding step and several `smoke-logic.js` assertions; iterating the fold by UTF-16 code unit instead of by code point (so a surrogate pair could be split) failed three of the lone-surrogate assertions inside smoke check (b), the rest being byte offsets the mutation happened not to land on. Privacy: appending `profile.name` to an entry's description failed the E2E step `calendar export — no profile, contact or business field is in the file`, and appending `ev.place` failed the same step — both caught by the E2E's direct text search of every `SUMMARY`/`DESCRIPTION` value, independent of the smoke harness's throwing-getter proof. Each mutation was reverted once the expected failure was confirmed.

Two implementation details follow from that mutation testing, not from the plan that proposed the step. `flow9.js`'s fold-boundary step decodes each physical line with `new TextDecoder("utf-8", { fatal: true })`, but a browser's `TextDecoder` cannot actually throw on invalid input — it substitutes a replacement character instead — so that decode call is a weaker check than it looks; the real guard against a fold splitting a multi-byte UTF-8 sequence is smoke check (b), which counts bytes directly. And the privacy step (`calendar export — no profile, contact or business field is in the file`) searches for every profile and business value in three forms — the raw downloaded text, the unfolded text, and the unfolded-and-unescaped text — because a value split across a fold boundary, or one containing an escaped character, would be invisible to a plain substring search of the raw bytes alone.

## Performance measurement rule
Single-run timings on this machine swing by ±50 % with background load. Compare builds only with `tools/e2e/ab.js` (two builds, one browser, interleaved rounds, medians). Structural counts (mounted rows, DOM nodes via `rows.js`) are reliable; wall-clock deltas under ±10 % are noise.

## Offline and updates
The production build ships a generated service worker (`dist/sw.js`): hashed assets cache-first, the document network-first with a cache fallback, and every non-current cache deleted on activate. A new deploy installs and takes control in the background; the running page is never reloaded for it, so the new build applies the next time the app is opened (decided 2026-09-13, after the reload dropped the user back on the home tab once per deploy). `navigator.storage.persist()` is requested at start so the records are not evicted under storage pressure. The E2E asserts both halves — that the worker controls the page, and that a reload with the network disabled still renders the app.

## Known limits
- No unit-test runner; engine checks are `smoke-logic.js` and the E2E. The planned file split (backlog 3) adds unit tests for `calcExamPayout`, `krProgress`, `migrate`.
- Dates use local time (`dstr`); a timezone change can shift streak boundaries.
- A session crossing midnight now re-reads the date on focus and on a 60-second tick, so `today` follows the clock; only a timezone change still shifts streak boundaries.
- Photos are stored as resized data URLs; very large evidence sets are bounded by `localStorage` quota (≈ 5 MB per origin). The backup file is the recovery path, and it is the user's job to write it out now and then.
- Installing from a different address creates a different origin, so the records do not follow; move them with a backup file.
- The portfolio image budget (`STORAGE_BUDGET`, 3.5 MB) is a heuristic guess at a slice of the same per-origin quota the state save also shares; a browser that blocks `localStorage` outright (private mode, disabled site data) fails the read-back check on every state change, not only on an image write, and surfaces the `저장에 실패했어요` toast every time rather than once (tracked in [exec-plans/tech-debt-tracker.md](exec-plans/tech-debt-tracker.md)).
- The calendar export (`캘린더로 내보내기`) writes a one-way snapshot: nothing completed, edited or deleted in the app after export reaches an already-imported calendar entry, and the app has no path to read a calendar back — see [design-docs/calendar-export.md](design-docs/calendar-export.md). Whether a given calendar app honours the file's `VALARM`s, and whether re-importing the same UID replaces, skips or duplicates the entry, both depend on that app and are unverified on a device — tracked as [TD-38](exec-plans/tech-debt-tracker.md) and backlog item 2, recorded (or `pending`) in [product-specs/install-and-backup.md](product-specs/install-and-backup.md).
