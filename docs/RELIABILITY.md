# Reliability
<!-- src: E2E --><!-- src: SPEC-10 -->

Reliability for a local-only app means: the user's state survives every version, the build never ships a broken flow, and measurements are believed only when they are reproducible.

## Persistence and migrations
- State is one JSON object under `localStorage["liferpg-state-v1"]` (adapter `store`, memory fallback when storage is unavailable). Images are separate keys: `liferpg-img-profile`, `liferpg-img-ev-{taskId}`, `liferpg-img-study-{taskId}-{n}`, `liferpg-img-folio-{id}` — removed with the task/portfolio entry and on full reset.
- Every schema change adds a sequential `if (s.v < N)` block; existing blocks are frozen and a non-numeric `v` is normalised to 0 first ([Rule 12](design-docs/core-beliefs.md#rule-12)). The ledger is generated in [generated/db-schema.md](generated/db-schema.md).

- Storage keys are never renamed; they are the compatibility contract.
- Writing a portfolio image goes through its own guard, independent of the state save: a file-size cap before decoding, an aspect-preserving resize (`resizeImageFit`, never upscales) with one quality retry over an output-length cap, a budget check against a 3.5 MB heuristic ceiling, then a write that is read back to confirm it survived (`saveImageChecked`). Every failure still saves the record without its image and toasts why, and the state-save effect itself now runs the same read-back check (`persisted(KEY)`) and toasts `저장에 실패했어요` when a state write did not reach `localStorage`.
- Saving a meeting or a project (schema v23; a meeting's `taskIds` since v24, at most 132 chars for ten links, counted inside the same record) goes through the same 3.5 MB heuristic ceiling (`STORAGE_BUDGET`), counted in string length against `storageUsedWith(state)` — the current in-memory `state` serialised, not `storageUsedBytes()` alone, because the state save persists one render behind ([product-specs/meetings.md](product-specs/meetings.md)). A save that would cross the budget is refused before any write, the form stays open with everything typed, and the tab always states its own usage (`저장 공간 {mb}MB / 3.5MB`) so the ceiling is never a surprise.
- Since schema v25 (2026-09-17), the same guard — renamed `recordFits` — also covers a meeting's progress entries (`,"progress":[]` + `,"aiHidden":false` add 31 chars to every meeting; a full 300-char entry adds ≈ 345, thirty of them ≈ 10,380) and every work item (≈ 150–200 chars each, no per-day cap since 2026-09-17); the `업무` tab states its own `저장 공간` line the same way ([product-specs/daily-work.md](product-specs/daily-work.md)).
- Since schema v26 (2026-09-17), a meeting's follow-up items add `,"followUps":[]` (15 chars) plus ≈ 90–292 chars per item (a full 200-char item with a due date and a work link ≈ 292; thirty ≈ 8,760); `commitMeeting` checks the meeting record **plus every work item its reconcile creates** against the budget in one call before writing either, so a mine follow-up cannot register a work item the budget would refuse ([product-specs/meetings.md](product-specs/meetings.md)).
- Also since 2026-09-17 (no schema bump — an optional field), a meeting's `transcript` adds `,"transcript":""` (15 chars) only when one exists, while `"projectId":null` (16) against a live id (24) makes a project-less memo 8 chars smaller; a full 30,000-char transcript with ~300 line breaks stringifies to ≈ 30,315 chars (each `\n` costs 2). Full transcripts alone: 3,672,064 / 30,315 ≈ **121** by the guard's own string-length unit, against ≈ **55** by the UTF-16-byte reading browsers actually meter `localStorage` in — the guard is a heuristic ceiling by its own comment, and this pre-existing gap is sharper now that one field can be 30,000 chars ([TD-59](exec-plans/tech-debt-tracker.md), accepted). `recordFits` already measures the whole record, transcript included; `clearTranscript` (`녹취록 지우기`) is the in-app way to reclaim the space.
- Since schema v27 (2026-09-17, [product-specs/documents.md](product-specs/documents.md)), top-level `documents[]` adds `,"documents":[]` (15 chars) once; one document ≈ 91 chars of overhead + title + summary (+ 12 with a `source`); a full document (60 + 120 + 5,000) ≈ 5,283 chars, a typical one ≈ 753 chars — two a week ≈ 75 k chars a year (2 % of the budget), one full document a working day ≈ 1.32 M a year (36 %). `recordFits` measures a document record whole.
- Also since schema v27 ([product-specs/schedule.md](product-specs/schedule.md)), an event's optional `checks[]` adds `,"checks":[]` (12 chars) the first time; one check ≈ 60 chars + text; thirty full 200-char checks ≈ 7,829 chars on one event, ten such events ≈ 78 k (2 %). `addCheck` / `importChecks` measure the event record as it will be written against its stored length, so ticking or deleting a check never trips the guard. The daily reader (`오늘 읽을 것`, schema v27, [product-specs/daily-reader.md](product-specs/daily-reader.md)) stores nothing at all — its `since` window is read from the pre-existing `act.briefingSeen` — but on a planted 2.13 M-char save (300 meetings × 30 follow-ups, 100 documents of 5,000 chars, 200 work items, 20 project events × 30 checks), `buildReader` ran in 3–7 ms and the modal's open-to-paint measured ≈ 54 ms, so the read side of this feature stays fast even at several times the storage budget's typical yearly growth.
- Since schema v28 (2026-09-17/18, tracks/roadmap/time budget/payments/role stages/pipeline/notices, [product-specs/business.md](product-specs/business.md), [product-specs/daily-work.md](product-specs/daily-work.md), [product-specs/meetings.md](product-specs/meetings.md)): `,"track":"work"` adds 15 chars per project/document/event/work item/memo, `,"track":"biz"` adds 14 per deal (a save with 200 events, 500 work items, 20 projects, 50 documents, 20 deals and 10 memos grows ≈ 12 k chars, 0.3 %); a milestone ≈ 120–900 chars depending on fields, the nine `ROADMAP_SEED` seeds ≈ 2.2 k once; a time-log entry ≈ 85 chars (+22 with `workId`), ≈ 27 k chars a year at one entry per working day (0.7 %); a payment line ≈ 75 chars (+21 with `paidAt`), twelve full lines ≈ 1.2 k on one deal; a lead ≈ 110–880 chars, fifty leads ≈ 13 k; a notice ≈ 110–820 chars, twenty a year ≈ 5 k; nine role stages with two conditions each ≈ 1.5 k once; `settings.bizHoursPerWeek` and the four new empty arrays add 89 chars once. Every milestone/lead/notice/time-log/payment-carrying write runs `recordFits`, the same 3.5 MB heuristic ceiling every other record kind shares.
- Since 2026-09-22 (no schema bump): `act.workRefreshedAt?` adds `,"workRefreshedAt":"YYYY-MM-DD"` (≈ 26 chars) once, only after the work bridge registers ≥ 1 proposal; `settings.checkNotify?` adds `,"checkNotify":true` (19 chars) once, only after the switch is touched; `meetings[].kind?` adds `,"kind":"training"` (19 chars) only on a training record — a meeting-kind record's storage footprint is unchanged. None of the three is measured against `recordFits` on its own (they ride the same meeting/settings/act writes that already run it, or write no record at all).
- Since 2026-09-18 (no schema bump — three more optional `role` fields, [design-docs/metrics-and-role-model.md](design-docs/metrics-and-role-model.md#storage-arithmetic)): `role.story` adds `,"story":""` (11 chars) plus up to `ROLE_STORY_MAX` (2,000) once; one `role.verdicts[]` entry is ≈ 130 chars of overhead (measured: an empty one is 140), ≈ 2.2 k full, ≈ 600 typical, and the array is capped at `ROLE_VERDICTS_MAX` (24, oldest dropped) — ≈ 53 k at the cap (1.4 % of the budget), ≈ 14 k typical; `role.seenStageK` adds `,"seenStageK":1` (15 chars). Every verdict save runs `recordFits(nextRole, JSON.stringify(prev.role || {}).length, "판정을")`, the same guard every other record kind shares. The fifth bridge packet itself (`buildRoleVerdictPacket`) is capped at `ROLE_PACKET_MAX` (12,000) with its own trim order — the demo packet measures 2,434 chars; a 12-stage, 5-condition-each fixture trims to 3,376; an untrimmable 260-area fixture stays at 16,325 because grades are never dropped.

## Verification pipeline (`npm run verify`)
`tools/harness/verify.js`: `vite build` → `vite preview` on a free port → `tools/e2e/run.js` (puppeteer-core driving the installed Chrome/Edge; no browser download) → parse `tools/e2e/out/<tag>-result.json`. Exit 1 on any failed step or console error. `--smoke` runs the pure-function engine checks first (`tools/harness/smoke-logic.js`: table integrity, longest-name matching, stage-group differential payouts, documented scenario payouts, and the calendar-export file builder — byte-counted folding, TEXT escaping, the monthly-clamp expansion, `RRULE`/`EXDATE` construction, alarms, and privacy by construction, plus (v28) the five new entry kinds — a follow-up's UID/summary, a check reminder the day before its occurrence, a milestone's due-day and D-7 entries, a payment line that never states its amount, a notice's deadline, the matching skipped counts, and a state without any v28 key still building; see [design-docs/calendar-export.md](design-docs/calendar-export.md)).

## Performance measurement rule
Single-run timings on this machine swing by ±50 % with background load. Compare builds only with `tools/e2e/ab.js` (two builds, one browser, interleaved rounds, medians). Structural counts (mounted rows, DOM nodes via `rows.js`) are reliable; wall-clock deltas under ±10 % are noise.

## Offline and updates
The production build ships a generated service worker (`dist/sw.js`): hashed assets cache-first, the document network-first with a cache fallback, and every non-current cache deleted on activate — **except** the `life-check` cache (2026-09-22), which `activate` keeps regardless of build id because it belongs to the [`확인 필요 notification`](product-specs/notifications.md), not to any one deploy. A new deploy installs and takes control in the background; the running page is never reloaded for it, so the new build applies the next time the app is opened (decided 2026-09-13, after the reload dropped the user back on the home tab once per deploy) — still true after the two handlers below, neither of which reloads a client. `navigator.storage.persist()` is requested at start so the records are not evicted under storage pressure. The E2E asserts both halves — that the worker controls the page, and that a reload with the network disabled still renders the app.

**The `확인 필요` notification's two handlers (2026-09-22).** `notificationclick` closes the tapped notification and either focuses an open client and posts it `{ open: "issues" }`, or, with none open, calls `clients.openWindow("./?open=issues")`. `periodicsync` (Chrome's own schedule, installed app only, tag `life-check`) re-shows the cached title/body when the entry is under 48 hours old, else a generic pair — the worker cannot read `localStorage`, so the page writes the rendered text into a Cache API entry on every state change and the worker only reads it back. Neither handler makes a network request.

## Known limits
- **Chrome, not the app, decides when a periodic sync fires** — the app asks for a floor (`minInterval`, 12 hours) through `periodicSync.register`, but Chrome's own engagement heuristics decide the actual moment, and the permission itself is granted only to an installed (added-to-home-screen) app; a browser tab, the dev server and the single-file demo never see it fire. The settings sheet states this in its caption (`설치된 앱에서만 주기 갱신이 돼요` / the always-shown `… Chrome이 정해요.` sentence) rather than promising a schedule the app cannot control.
- **Headless Chrome does not reliably surface a shown notification** to `ServiceWorkerRegistration.getNotifications()` even immediately after `showNotification` resolves — `tools/e2e/flow6.js`'s check-notification step records the count in its own `metrics`, not as a pass/fail assertion, and instead asserts the thing the app actually controls: the `life-check` Cache API entry's title/body/counts. A real-device check of the notification actually appearing (and of Periodic Background Sync actually firing over hours, not simulated through CDP) is unverified and tracked alongside backlog item 2.
- The `life-check` Cache API entry can be evicted by the browser at any time, with no consequence beyond the next open re-showing the generic periodic-sync pair until the page rebuilds it — by design, the same "rebuildable mirror" treatment every other derived value gets ([Rule 9](design-docs/core-beliefs.md#rule-9)).
- No unit-test runner; engine checks are `smoke-logic.js` and the E2E. The planned file split (backlog 3) adds unit tests for `calcExamPayout`, `krProgress`, `migrate`.
- Dates use local time (`dstr`); a timezone change can shift streak boundaries.
- A session crossing midnight now re-reads the date on focus and on a 60-second tick, so `today` follows the clock; only a timezone change still shifts streak boundaries.
- Photos are stored as resized data URLs; very large evidence sets are bounded by `localStorage` quota (≈ 5 MB per origin). The backup file is the recovery path, and it is the user's job to write it out now and then.
- Installing from a different address creates a different origin, so the records do not follow; move them with a backup file.
- The portfolio image budget (`STORAGE_BUDGET`, 3.5 MB) is a heuristic guess at a slice of the same per-origin quota the state save also shares; a browser that blocks `localStorage` outright (private mode, disabled site data) fails the read-back check on every state change, not only on an image write, and surfaces the `저장에 실패했어요` toast every time rather than once (tracked in [exec-plans/tech-debt-tracker.md](exec-plans/tech-debt-tracker.md)).
- The calendar export (`캘린더로 내보내기`) writes a one-way snapshot: nothing completed, edited or deleted in the app after export reaches an already-imported calendar entry, and the app has no path to read a calendar back — see [design-docs/calendar-export.md](design-docs/calendar-export.md). Whether a given calendar app honours the file's `VALARM`s, and whether re-importing the same UID replaces, skips or duplicates the entry, both depend on that app and are unverified on a device — tracked as [TD-38](exec-plans/tech-debt-tracker.md) and backlog item 2, recorded (or `pending`) in [product-specs/install-and-backup.md](product-specs/install-and-backup.md).
