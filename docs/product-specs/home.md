# Home tab
<!-- src: SPEC-4-2 -->

The first section is the 오늘 브리핑 card (see [daily-briefing.md](daily-briefing.md)). `HomeTab` is the landing screen after onboarding: a profile card, the three most urgent active goals with their 페이스 (pace), and up to five of today's open 실행 (tasks) with a one-tap completion that still goes through the evidence gate. Everything is derived from `state` at render time — nothing is stored ([Rule 9](../design-docs/core-beliefs.md#rule-9)). Props: `state, today, imgs, onProfile (opens ProfileModal), onComplete (tryComplete), onGoGoals, onGoQuests, onGoSchedule, onGoBiz` — the last four switch the bottom tab to 목표 / 실행 / 일정 / 사업.

## Profile card
- Portrait: `Portrait` at size 72 renders `imgs.profile` when a photo exists, otherwise the parametric `PortraitSprite` from `profile.look` and `profile.gender`. The card carries no photo control of its own any more — registering and clearing the photo both moved into the profile modal below (2026-09-13).
- Control: a single `프로필` button (replaces the old `업로드` button and its `✕` photo-clear overlay) opens `ProfileModal` (`onProfile` → `modal.type = "profile"`). The photo, the personal facts and the whole CV are all edited there; the card states facts and points at the one screen that owns them.
- Text: `{displayName(state.profile)}` (nickname, else name, else `사용자`; `profile.nick` is no longer read directly here or anywhere else on screen); one line listing every 영역 (area) as `{area.name} {RANKS[grade].name}` joined by ` · `; `오늘 {doneToday}건 완료`, where `doneToday` = `daily` tasks whose `doneDates` includes `today` + `once` tasks with `doneAt === today`.
- The streak `🔥 {act.streak}일` (amber) and 보호권 (streak shields) `🛡 {act.shieldsLeft}` are not on this card: `App` renders them in the header of every tab, next to `{displayName(state.profile)} · status`.

## Profile modal (`modal.type: "profile"`) — the CV
`ProfileModal` is the only screen that can change anything about the user after onboarding. Before it existed the app's sole post-onboarding profile control was the home card's `업로드` button, and there was no way to correct a name, add a school or a job, or clear the photo, short of `데이터 초기화` ([growth.md](growth.md)). It reuses the same entry-list-plus-inline-add-form pair onboarding uses — `CvSection` / `CvAddForm` / `CvEntryRow`, factored once so the two screens cannot drift apart — plus the shared `OptRow` chip row. Props: `profile, state, img, today, onUpload` (the root's `askUpload("profile")`), `onClearImg` (`clearImg("profile")`), `onSave` (`saveProfile`), `onClose`.

Title `프로필`. It opens with the standing note `학력·경력을 고쳐도 시작 등급은 바뀌지 않아요. 승급은 관문 증거로만 올라가요.` — editing the CV is never a promotion path ([Rule 4](../design-docs/core-beliefs.md#rule-4), [Rule 11](../design-docs/core-beliefs.md#rule-11)).

| Section | Contents |
|---|---|
| `사진` | `Portrait` at size 64, `사진 등록` (calls the root's `askUpload("profile")`) and, once a photo exists, `사진 삭제` (`onClearImg`). The modal declares no `<input type="file">` of its own — both buttons drive the one hidden input mounted on `Shell`, outside every modal, so the modal closing mid-pick cannot take the input with it. Onboarding itself has no photo step at all (`사진은 시작한 뒤 홈 프로필 카드에서 등록해요.`), so this is the only photo entry point in the app. An E2E step (`tools/e2e/flow3.js`) asserts no `input[type="file"]` exists inside the open modal (`.fixed.inset-0`) before clicking `사진 등록`, guarding this new surface against a regression of the same shape as [R-14](../exec-plans/tech-debt-tracker.md) (a file input mounted inside a modal instead of the root, which crashed a different screen in 2026-09-09). |
| `인적사항` | `이름`, `닉네임 (선택)`, `생년월일` (`input type="date"`, with `{ageText({ birth }, today)}` printed beneath it — derived at render, never stored, [Rule 9](../design-docs/core-beliefs.md#rule-9)), `성별`, `현재 신분` (`STATUS_OPTS`), `이메일 (선택)`, `연락처 (선택)`. |
| `학력` | The same `CvSection kind="edu"` list and add form as onboarding step 0 — fields and validation in [new-user-onboarding.md](new-user-onboarding.md). |
| `경력` | The same `CvSection kind="career"` as onboarding step 4, plus the derived line `합산 실무 {careerText(careerMonths(careers, today))}` — deliberately without onboarding's `· 시작 등급 기준 {label}` clause, since no grade is recomputed here. |
| `보유 기록` (read-only) | `자격 {n}건` listing `profile.certs`; `시험 성적 {n}건` listing `state.exams.best` as `{fam.n} {label}`; `포트폴리오 {n}건` counting `state.folio`; each prints `없음` when empty. Note: `여기서는 고칠 수 없어요 — 자격·시험은 목표의 핵심결과에서, 포트폴리오는 사업 탭에서 관리해요.` |

Validation on `저장`, checked in this order: name empty → `이름을 입력해 주세요.`; birth empty → `생년월일을 입력해 주세요.`; birth malformed → `생년월일 형식이 올바르지 않아요 — YYYY-MM-DD로 입력해요.`; birth after today → `생년월일이 오늘보다 뒤예요.`; gender or status missing → `성별과 현재 신분을 선택해 주세요.`; no education entry → `학력을 1개 이상 추가해 주세요.`; malformed e-mail → `이메일 형식이 올바르지 않아요.` (the phone field has no format check). The `학력` / `경력` add-form validation is identical to onboarding's.

`저장` calls `onSave` with exactly nine fields — `name, nick, birth, gender, status, email, phone, edus, careers`, trimmed where applicable. The handler, `saveProfile`, merges only those nine keys into `state.profile` through the clone pattern; it never touches `profile.edu`, `profile.career`, `certs`, `examsOwned`, `look`, or any `areas[].grade`. This is the load-bearing invariant of the whole feature — **a CV edited after onboarding moves no grade** ([Rule 4](../design-docs/core-beliefs.md#rule-4), [Rule 11](../design-docs/core-beliefs.md#rule-11)) — proven by an E2E step (`profile modal — a CV edit never moves a grade`) that reads every `areas[].grade` plus `profile.edu` / `profile.career` before adding a `박사` `졸업` entry and saving, then asserts both are byte-identical afterwards; the step was mutation-tested by deliberately adding a `profile.edu` rewrite and a grade bump inside `saveProfile`, which failed it as expected ([RELIABILITY.md](../RELIABILITY.md)). Toast `프로필을 저장했어요`. Closing without saving discards every change: `창을 닫으면 저장되지 않아요.` is printed under the button.

## 오늘 브리핑 card
Three mono lines and, when one exists, the first severity-3 line of the briefing in rose. The second mono line is
a button: `오늘 일정 {n}건 · 3일 내 마감 {n}건 ›` (`brief.counts.events` / `brief.counts.dueSoon`, the 3 read from
`EVENT_SOON_DAYS`) → `onGoSchedule` switches to the 일정 tab. The third, reading the same `buildBriefing` call:
`이번 달 계약 {won} · 입금 미확인 {n}건 ›` (`brief.counts.bizMonth` / `brief.counts.bizUnpaid`, the unpaid count
rose when above zero) → `onGoBiz` switches to the 사업 tab. Both are date/money facts that belong beside the other
today numbers, which is why they are lines here instead of a fifth and sixth card. Full card:
[daily-briefing.md](daily-briefing.md); the tabs themselves: [schedule.md](schedule.md), [business.md](business.md).

## 오늘의 초점 (today's focus)
`SectionLabel` in cyan with `전체 보기 ›` (→ goals tab). `focus` = active goals sorted ascending by `deadline || "9999"` (undated goals last), first 3.
- No active goal: `EmptyGoalSvg`, `목표 없음 — 진행률을 계산할 대상이 없습니다.`, button `첫 목표 세우기` (→ goals tab).
- Each card is one button (→ goals tab): title + `ddayStr(deadline)` (`D-{n}` / `D-DAY` / `D+{n}`, empty when undated); `Bar(pc.p)` in `bg-cyan-400`; a mono line `진행 {round(p·100)}%`, then ` · 시간 경과 {round(el·100)}%` only when `pc.el` is not null (deadline and `createdAt` present), then ` · {pc.label}` in `pc.cls`. `pc = paceOf(goal, state)`: `gap = round((p − el)·100)`; label `{−gap}%p 뒤처짐` (rose) when `gap ≤ −5`, `{gap}%p 앞섬` (emerald) when `gap ≥ 5`, else `궤도 유지`; `기한 없음` without a deadline. Formulas: `goal-engine.md` in `../design-docs/`. Pace is never hidden ([Rule 13](../design-docs/core-beliefs.md#rule-13)).

## 오늘 할 일 (today's tasks)
The card reads the same expansion the `실행` tab reads (`todoOf(state, today)`), so the two can never disagree about what "today" means: `todayQuests` is the `overdue` and `today` groups' rows, filtered to `kind === "task"` and mapped back to the task. This is narrower than the tab: `실행` also owns `내일` / `이번 주` / `이후` and the schedule/business rows, both of which already have their own lines above this card (`오늘 일정 {n}건 · 3일 내 마감 {n}건 ›`, `이번 달 계약 … · 입금 미확인 {n}건 ›`). Rendering below `todayQuests.slice(0, 5)` is unchanged. Each row shows a `DueChip`: `기한 지남` (rose) when the date has passed, otherwise `ddayStr(due)` with `D-DAY` amber for today.
`SectionLabel` (`오늘 할 일`) with `관리 ›` (→ tasks tab). Empty: `오늘 기한인 실행이 없어요 — 이번 주 이후는 실행 탭에 있어요.`
- Row: a check button (`Check` icon drawn `text-transparent`) → `onComplete(q)` = `tryComplete`, which opens `StudyVerifyModal` (`isStudy`), `ActivityLogModal` (`kind`), or `EvidenceModal` (`needsEvidence`) before `completeTask` runs — [Rule 10](../design-docs/core-beliefs.md#rule-10), [Rule 16](../design-docs/core-beliefs.md#rule-16), [Rule 17](../design-docs/core-beliefs.md#rule-17); the goal-delta toast comes from `completeTask`, not from this tab. Title with kind prefix `📚 ` / `💪 ` for `book` / `fit`; subtitle `{area.name}[ · 🎯 {goal.title}][ · 매일]`, plus ` · 목표 연결 없음` when the task has no goal. Right side: `isExam` → `시험 D{band.d}`, `isCert` → `자격 D{certD}` (both coloured by `GRADE_TEXT` / `GRADE_BORDER` of `achGrade(d)`), otherwise `DiffBadge(diff)`.
